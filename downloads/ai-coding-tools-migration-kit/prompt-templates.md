# 跨工具通用代码提示词模板

这些模板不依赖特定 AI 编程工具，可在 GitHub Copilot、Claude Code、Cursor、Qwen Code 等任何工具中使用。核心原则是：写清楚目标、上下文、约束和验收标准。

## 1. 代码补全模板

### 函数/方法补全
```
请为以下函数补全实现：

函数签名：{函数签名}
功能描述：{这个函数要做什么}
输入参数：{参数名} - {参数含义和类型}
返回值：{返回值含义和类型}
约束条件：
- {约束1，如"不使用第三方库"}
- {约束2，如"时间复杂度不超过 O(n log n)"}
- {约束3，如"需要处理空输入的边界情况"}

相关代码上下文：
{粘贴相关的类定义、依赖函数或类型定义}

请给出完整实现，并在关键步骤添加注释。
```

### 类/组件补全
```
请实现以下类/组件：

类名：{类名}
继承/实现：{父类或接口}
职责：{这个类负责什么}
必需的方法：
- {方法1}：{用途}
- {方法2}：{用途}

设计约束：
- {约束1，如"遵循单一职责原则"}
- {约束2，如"依赖通过构造函数注入"}
- {约束3，如"公共方法需要参数校验"}

现有代码：
{粘贴已有的接口、基类或相关代码}

请给出完整实现，包含必要的导入和类型注解。
```

## 2. 代码审查模板

```
请审查以下代码，从以下维度给出反馈：

1. 正确性：是否有逻辑错误、边界情况未处理
2. 安全性：是否有注入、越权、敏感信息泄露等风险
3. 性能：是否有明显的性能瓶颈或可优化点
4. 可读性：命名、结构、注释是否清晰
5. 可维护性：是否易于扩展和修改
6. 最佳实践：是否符合语言/框架的最佳实践

代码：
{粘贴要审查的代码}

上下文：
- 这是项目中的{模块/功能}
- 使用的技术栈：{语言/框架/库}
- 这段代码的调用方：{谁会调用它}

请按严重程度排序（严重/中等/建议），每条给出具体位置和修改建议。不要只说"可以优化"，要给出具体的优化方案。
```

## 3. Bug 修复模板

```
请帮我定位并修复以下 Bug：

问题描述：{用户可见的问题现象}
预期行为：{应该是什么样}
实际行为：{实际是什么样}

复现步骤：
1. {步骤1}
2. {步骤2}
3. {步骤3}

错误信息：
{粘贴完整的错误堆栈或控制台输出}

相关代码：
{粘贴可能相关的代码文件，标注文件路径}

环境信息：
- 语言/框架版本：{版本号}
- 操作系统：{系统}
- 其他相关依赖：{依赖和版本}

请先分析可能的原因，再给出修复方案。如果有多种可能，请按可能性排序。修复后请说明如何验证修复有效。
```

## 4. 重构模板

```
请帮我重构以下代码：

重构目标：{如"提高可读性"、"减少重复"、"提升性能"、"分离职责"}
当前问题：{代码现在有什么问题}
保持不变：{哪些行为和接口不能改变}

代码：
{粘贴要重构的代码}

上下文：
- 这是{项目/模块}中的代码
- 调用方：{谁在使用这段代码}
- 测试覆盖：{是否有测试，测试是否充分}

约束条件：
- {约束1，如"保持公共 API 不变"}
- {约束2，如"不引入新的第三方依赖"}
- {约束3，如"重构后需要能通过现有测试"}

请给出重构后的完整代码，并说明：
1. 做了哪些改动
2. 为什么这样改
3. 有哪些潜在风险
4. 如何验证重构没有破坏原有功能
```

## 5. 测试生成模板

```
请为以下代码生成单元测试：

被测代码：
{粘贴要测试的函数/类}

文件路径：{源文件路径，用于确定测试文件位置}
技术栈：{测试框架，如 pytest、jest、JUnit}

测试要求：
- 覆盖正常流程
- 覆盖边界情况（空输入、最大值、最小值等）
- 覆盖异常/错误情况
- 每个测试用例有清晰的命名，说明测试什么场景
- 使用 Arrange-Act-Assert 结构
- 不要测试实现细节，只测试公共行为

依赖说明：
- {外部依赖1}：是否需要 mock，如何 mock
- {外部依赖2}：是否需要测试数据

请给出完整的测试文件代码，并在注释中说明每个测试用例的意图。如果有难以测试的部分，请说明原因并给出替代方案。
```

## 6. Agent 任务模板（多步骤）

```
请帮我完成以下任务：

任务目标：{最终要达成什么}
任务背景：{为什么要做这件事}

具体要求：
1. {要求1}
2. {要求2}
3. {要求3}

项目结构：
{列出相关的目录和文件，或让 Agent 先探索项目}

技术约束：
- {约束1，如"使用项目已有的技术栈"}
- {约束2，如"遵循项目的代码风格"}
- {约束3，如"不修改不相关的文件"}

验收标准：
- {标准1，如"功能正常运行"}
- {标准2，如"通过现有测试"}
- {标准3，如"代码通过 lint 检查"}

请按以下步骤执行：
1. 先探索项目结构，理解相关代码
2. 制定实现计划，列出要修改的文件
3. 逐步实现，每步说明做了什么
4. 完成后自我检查，确认满足所有验收标准
5. 给出最终的修改总结和验证方法

在执行过程中，如果遇到不确定的地方，请先询问而不是假设。如果需要运行命令或修改文件，请先说明意图。
```

## 使用技巧

1. **上下文越具体越好**：粘贴相关的类型定义、接口、调用方代码，比只给一个函数效果好得多
2. **写清楚约束**：明确说"不能用第三方库"、"必须兼容旧版本"、"时间复杂度要求"等
3. **要求解释**：不要只要代码，要求解释为什么这样写，帮助你理解和验证
4. **分步骤执行**：复杂任务拆成多步，每步确认后再继续，比一次性给大任务效果好
5. **提供反例**：如果有不想要的写法，明确说"不要用 XX 方式，因为 XX"
6. **验证结果**：拿到代码后自己跑一遍测试和 lint，不要假设 AI 写的一定对
