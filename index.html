Copilot 代码评审全面 API 化：企业、组织、仓库三层都能用 REST 与 GraphQL 管

GitHub 把 Copilot 代码评审的设置搬进了 REST 与 GraphQL API，粒度分三层：企业管理员可全局开关，或把选择权下放给组织；组织管理员可管启用状态、默认评审强度与 runner 配置；仓库管理员可管评审强度、是否使用自定义指令与 MCP 工具。API 同时增加归属字段，能识别哪些评审和评论来自 Copilot、这次用了哪一档强度、评论引用了哪些 skills、MCP server 与自定义指令。网页端评审概览也改版了：评审强度与问卷收进紧凑页脚，跳过和被排除的文件合并成一个区块，空区块直接省略。

GitHub Changelog 2026年11月5日

Copilot 用量指标 API 新增代码评审「处置率」：评论有没有被照做，终于能算出来

企业和组织的仓库级 Copilot 用量报表里，每条 repos-1-day 记录新增 copilot_code_review 对象：total_comments_evaluated 是接受评估的评审评论数，total_comments_addressed 是开发者确实处理过的数量，两者相除就是处置率。还提供按严重度、评审强度、评论类型（bug、security、自定义规范）和自定义来源（自定义指令、skills、MCP server）的拆分，以及 total_merged_no_human_change_request_after_review，统计 Copilot 评审后没有人再要求修改就合并的 PR 数。

今天 10 分钟能学什么

把「Copilot 代码评审全面 API 化：企业、组织、仓库三层都能用 REST 与 GraphQL 管」变成一个可验证动作

不追热点名词，先学会核对来源、判断影响范围，再在自己的工具或项目里完成一个低风险检查。

  1. 打开一手来源，只记录发布日期、影响对象和需要核对的配置。
  2. 用 AI 工具来源核验表检查权限、数据边界、费用或模型依赖。
  3. 在自己的项目里做一次只读验证，例如查看默认模型、配置项或日志。
  4. 写下结论：继续使用、暂缓使用，或需要回滚到原方案。
