GitHub Changelog 2026年11月11日

Issue 类型与字段下放到个人账号：个人仓库也能建 Bug、Task、Feature 和自定义字段

GitHub 把 Issue types 与 issue fields 正式开放给个人账号拥有的仓库，个人开发者和开源维护者可以用同一套规划能力整理跨仓库的 issue。类型可在个人账号设置的 Planning 下自定义，默认是 Bug、Task、Feature，最多 25 个；字段默认 Priority、Effort、Start date、Target date，最多 25 个，支持文本、数字、日期、单选与多选，还能把字段固定到某个类型或让无类型 issue 也能用。新建或查看 issue 时可直接选类型和字段，也能在 Projects 里做自定义视图和批量修改，REST、GraphQL 与 webhook 都能程序化管理。另外，现在可以在 issue 里直接创建标签和里程碑，不用跳去仓库设置页。

GitHub Changelog 2026年11月10日

Dependabot 将暂停一年无活动的仓库：告警归档不删除，一次 push 就能恢复

从 2026 年 12 月 8 日起，GitHub 会对大多数「过去一年没有任何活动」的仓库关闭 Dependabot 告警，已有告警归档而不是删除，随时可以恢复。官方把活动定义为：向任意分支或标签 push、创建仓库、开启 Dependabot 告警，三者任一即可。恢复很简单：任何一次 push 会自动重新开启，也可以在仓库设置里手动打开，归档告警会恢复且一年计时重新开始。如果仓库启用了强制安全配置且其中包含 Dependabot 告警，或企业策略不允许仓库管理员开关告警，则不会被关闭。该变更覆盖 github.com 所有套餐与带数据驻留的 Enterprise Cloud，不适用于 GitHub Enterprise Server。

今天 10 分钟能学什么

把「Issue 类型与字段下放到个人账号：个人仓库也能建 Bug、Task、Feature 和自定义字段」变成一个可验证动作

不追热点名词，先学会核对来源、判断影响范围，再在自己的工具或项目里完成一个低风险检查。

  1. 打开一手来源，只记录发布日期、影响对象和需要核对的配置。
  2. 用 AI 工具来源核验表检查权限、数据边界、费用或模型依赖。
  3. 在自己的项目里做一次只读验证，例如查看默认模型、配置项或日志。
  4. 写下结论：继续使用、暂缓使用，或需要回滚到原方案。
