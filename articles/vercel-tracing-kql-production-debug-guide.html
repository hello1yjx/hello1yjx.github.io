Vercel Tracing 正式可用：用 KQL 从慢请求追到具体 span

2026年11月8日 11 分钟 作者：Avery Lin

日志能告诉你出错了，却很难告诉你两秒钟花在哪一层。Vercel Tracing 11 月 6 日转为正式可用，所有套餐都能用：新的 Traces 页面把 trace 与 span 集中展示，支持项目级或团队级范围、KQL 过滤和 Live 模式；CLI 提供 search、inspect、config 三个命令，与网页共用同一套查询语法。Next.js 16.5 起新建项目首次构建成功后自动开启追踪。这篇教程讲清 trace 与日志的分工、采样怎么配、KQL 怎么写，并用一个慢接口案例走完排障全程。

来源与增量价值

本文基于官方资料整理，并补充适用场景、限制条件和实践检查步骤。

首要来源：Vercel Tracing is now generally available。事实以原始来源为准，本站建议需结合自己的环境验证。

线上接口变慢，第一反应是翻日志。可日志是离散事件，你能看到「请求完成」，却看不出边缘路由、缓存、函数执行各占了多少时间。Serverless 把一次请求拆到多个组件，这个问题更明显：错误日志指向函数，真正的瓶颈可能在前面某一层。

Vercel Tracing 在 11 月 6 日转为正式可用，把 trace 与 span 放到同一个页面，还给 CLI 配了同一套 KQL。这篇教程按「trace 是什么 → 怎么开 → 怎么查 → 怎么调优」推进，最后用一个慢接口案例把查询串起来，读完可以直接在自己项目里复现。

这篇内容适合谁

  • 在 Vercel 上跑 Next.js、遇到性能问题只能靠日志猜的开发者
  • 需要给团队建立一套统一排障入口的负责人
  • 想把 trace 查询固化进巡检脚本的运维同学

实践与验证步骤

  • 分清日志与 trace 各自回答什么问题
  • 了解正式版新增的页面、命令与留存变化
  • 确认项目是否已开启追踪与采样
  • 在仪表盘里打开第一条 trace 并读懂瀑布
  • 掌握常用 KQL 查询写法
  • 把同一套查询搬到 CLI 做批量检索
  • 避开自动开启、留存与采样的边界
  • 用一个真实慢接口完成端到端排障

重点判断与使用建议

  • 所有套餐可用，价格与 beta 阶段保持一致
  • Traces 页面统一展示 trace 与 span，可在项目或团队范围切换
  • 支持 Spans 与 Traces 两种列表视图，各自可过滤
  • KQL 搜索，Live 模式可流式查看新产生的 trace
  • vercel traces search --query 与仪表盘共用同一套 KQL
  • vercel traces inspect 查看单条 trace 的细节
  • vercel traces config 管理项目的采样规则
  • Next.js 16.5 起，新建且含至少一个 Node.js 函数的项目首次构建成功后自动开启
  • 自动开启会注入一条 100% 采样的规则，并在构建时注入 instrumentation
  • 留存：Hobby 3 天、Pro 与 Enterprise 14 天

一、trace 与日志解决的不是同一个问题

  • 日志是离散事件，能回答「发生了什么」
  • trace 是调用链，能回答「时间花在哪一层」
  • 一次请求跨边缘路由、缓存、函数执行，日志之间对不上号
  • span 是链路中的一段，带服务名与耗时，是可比较的最小单位
  • 排障顺序通常是先看错误日志定位现象，再拉 trace 定位层级
  • 两者都缺时不要硬猜，先补观测再优化代码

二、正式版带来了什么

  • 所有套餐可用，定价与 beta 阶段相同，不必重算预算
  • 新增 Traces 页面，把散落在日志里的 trace 集中起来
  • 支持项目级与团队级两种范围，跨项目问题也能查
  • Spans 与 Traces 两种视图，一个看细节一个看整体
  • KQL 过滤加 Live 模式，复现中的问题可以边跑边看
  • CLI 补齐 search、inspect、config，脚本化成为可能
  • 留存时间整体延长，事故回溯不再只有一小时窗口

三、开通与确认采样

  • beta 阶段不配采样规则就什么都不收，这是最常见的「没数据」原因
  • 正式版对新建 Next.js 项目默认开启，存量项目仍需手动加规则
  • 自动开启的条件是 Next.js 16.5 起、至少一个 Node.js 函数、首次构建成功
  • 默认注入一条采样 100% 请求的规则，所有环境都生效
  • 构建时注入 instrumentation，框架 span 不需要手工埋点
  • 确认方式：Traces 页面能查到数据，且时间范围与采样规则一致

四、仪表盘里查第一条 trace

  • 先进入项目的 Traces 页面，确认范围选的是项目还是团队
  • 用 Traces 列表看整体分布，再用 Spans 列表看单段耗时
  • 把时间范围缩到出问题的那几分钟，避免被正常流量淹没
  • 打开单条 trace 看瀑布图，从总耗时往下逐层拆
  • 找耗时最长的 span，而不是第一个标红的 span
  • 记下可疑 span 的服务名与名称，作为下一步过滤条件

五、KQL 写法与常用查询

  • span.name:db* AND span.duration > 500 用来找慢数据库段
  • span.duration > 2000 找超过两秒的段，适合先粗筛
  • 加 --status error 与 --since 1h 找最近一小时内的错误
  • 布尔组合与通配符要收窄范围，全量扫描既慢又费额度
  • 字段名以实际 schema 为准，先小范围试再扩大
  • 把验证过的查询存成模板，团队共用一套口径

六、CLI 与仪表盘共用查询

  • vercel traces search --query 接受与页面相同的 KQL，写好就能搬
  • 默认搜整个团队，加 --project 限定到单个项目
  • vercel traces inspect 看单条 trace 的完整细节
  • vercel traces config 管理采样规则，不必回网页点
  • 把常用查询写进脚本，做成定时巡检与告警前置
  • CI 里只做只读查询，避免脚本误改采样配置

七、Next.js 自动开启的边界

  • 只覆盖新建项目，存量项目不会因为升级自动获得数据
  • 只对至少含一个 Node.js 函数的项目生效，纯静态站点不触发
  • 首次成功构建之后才开启，之前的请求没有 trace
  • 100% 采样在生产环境通常偏重，需要按流量调整
  • 退出方式是删掉所有采样规则，只删一条不够
  • 所有环境都会开，测试环境的噪声也会进入同一视图

八、留存、成本与采样权衡

  • Hobby 保留 3 天，Pro 与 Enterprise 保留 14 天
  • 采样率直接决定数据量与成本，满采样只适合低流量项目
  • 高频接口降采样，关键链路保持高采样
  • 留存决定你能回看多久，事故复盘常发生在几天之后
  • 观测数据本身含请求参数，注意隐私与合规边界
  • 按周复核一次数据量，比出事时才发现超额更省心

九、排障案例：一次慢接口

  • 现象：某个 API 路由的 P95 从 300 毫秒涨到 2 秒
  • 第一步用 KQL 过滤该路由相关的 span，限定到故障时间段
  • 瀑布显示函数执行占 1.6 秒，边缘路由与缓存都正常
  • 继续下钻函数内部 span，定位到一次外部请求耗时异常
  • 修复后取同时段 trace 对比，确认总耗时回落到基线
  • 把这条查询固化成巡检脚本，下类似问题直接跑

十、上线检查清单

  • 确认采样规则覆盖了需要观察的环境
  • 确认留存期满足团队的回溯习惯
  • 关键路由补自定义 span，命名统一便于过滤
  • 常用 KQL 写进 runbook，新人照抄可用
  • 设置成本观察项，按周复核数据量
  • 让团队成员都知道排障从哪个页面开始
